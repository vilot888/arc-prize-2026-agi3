### 评分公式（官方，用于理解优化目标）

单关：`s_i = min(1.15, (h_i / a_i)²)`，其中 `h_i` = 人类基准动作数，`a_i` = agent 动作数。
整局：`S = 100 × min(Σ(i·s_i)/W, Σ_{已通关} i / W)`，`W = n(n+1)/2`。
总分 = 各游戏 `S` 的算术平均。

⇒ **得分 ≈ 9 小时预算内能覆盖多少游戏 × 每游戏动作效率。**

## 3. 我们的贡献

### 3.1 启动超时诊断与修复（本方案唯一的实质性代码改动）

**问题**：所有 0.00 分的提交都来自同一原因——模型冷启动时间超过 harness 的等待上限。

**量化**：harness 有两层等待，容易被误解为只有一层：

```
第 1 层  SERVER_STARTUP_TIMEOUT     = 720s   (等 /health 返回 200)
第 2 层  ARC3_HTTP_RETRY_INITIAL    = 900s   (每个 agent 首次请求前的宽限)
─────────────────────────────────────────────
总容忍 = 27 分钟
```

而模型冷启动实测 **18 ~ 37 分钟**（两次独立观测）。**27 < 37 → 结构性不足**，不是概率问题。

**修复**（`notebooks/arc3-form-d1-t55.ipynb`）：

```python
SERVER_STARTUP_TIMEOUT = 55 * 60        # 720  -> 3300 秒
os.environ['ARC3_HTTP_RETRY_INITIAL_SECONDS'] = '3600'   # 900 -> 3600 秒
```

**效果**：总容忍 27 分钟 → 115 分钟，余量 78 分钟。

**实测对照**（同一账号）：

| 内核 | 总容忍 | 提交数 | 0.00 次数 |
|---|---|---|---|
| form_d1 原版（720s） | 27 min | 8 | **2**（另有 1 次 10.32 半启动） |
| 三个修复版（3300s） | 70 ~ 115 min | 6 | **0** |

### 3.2 参数消融：`analyzer_timeout`

在 lalalia 基座上把 `bm.solver.analyzer_timeout` 从 900s 提到 3600s（当初动机是"对齐某公开方案"），同账号对照：

- 900s 版：**26.95**
- 3600s 版：**25.51**（−1.44）

⇒ **该参数不是瓶颈**。合理解释：9 小时预算固定，单关分析放宽后会挤占其他游戏的探索时间，覆盖率下降。

### 3.3 调度器补丁的对照结论

有两条不同的补丁常被混淆，我们用同账号实测区分：

| 补丁 | 实测 | 结论 |
|---|---|---|
| shiiin9 D'（`A·M·C+B·φ` 公式） | 引用作者的公开对照：lalalia 无补丁 33.94 → 加 D' 23.57（−10.37） | **负收益，不采用** |
| form_priority（`eff_const=100` 那套） | 我方：lalalia 25.59/23.06 → +form_priority 26.95/25.51（+1.5 均值） | 小幅正收益，采用 |

### 3.4 选票决策（Final Submission 选择）

在"两份取 max、出错丢弃"的机制下，第二槽的价值是**兜底**。我们按"私有榜铜线敏感性"建模：

| 私有铜线 | 同内核双份（32.61+30.64） | 异内核（32.61+26.95） |
|---|---|---|
| ≤25 | 75~86% | **100%** |
| 27 | **61%** | 37.5% |
| 31.6 | **23.4%** | 12.5% |

因 32.61 那份的内核存在 25% 归零率（720s），双份同内核的双零风险为 6.25%，且**0 分不可逆**（排名垫底 = 必然无牌）。最终选择 **32.61 + 26.95**：上不封顶、下有保底、永不 0 分。

### 3.5 平台故障期的识别

赛程末期 RTX 6000 实例出现启动时间 10~60 分钟随机、慢实例后段再慢 ~10% 的现象（社区第 3 名独立实测，多帖侧证）。这解释了同期集体性的分数下滑与 0 分聚集，**不代表方案本身退化**。

## 4. 实验记录

全部 21 次提交的分数分布（同一账号、同一竞赛）：

| 内核族 | 发数 | 分数 | 中位 | 归零率 |
|---|---|---|---|---|
| form_d1（720s） | 8 | 32.61 / 30.64 / 27.05 / 25.18 / 24.22 / 10.32 / 0.00 / 0.00 | 26.1 | **25%** |
| slm-plus（3300s） | 2 | 26.95 / 25.51 | 26.2 | **0%** |
| form-d1-t55（3300s） | 2 | 26.31 / 22.14 | 24.2 | **0%** |
| lalalia-final（3300s） | 2 | 25.59 / 23.06 | 24.3 | **0%** |
| d-prime 系（2400s） | 3 | 27.53 / 24.44 / 24.99 | 24.99 | 0% |
| d-prime v1 | 2 | 27.91 / 26.16 | 27.0 | 0% |
| 其他 | 2 | 0.00 / 0.00 | — | — |

**主要观察**：
1. 同一内核的单次波动极大（σ ≈ 3.8），**单次高分多为上尾抽样**，不代表能力均值。
2. **启动超时是唯一可被工程手段消除的失败源**——修复后归零率归零。
3. 不同基座（dfranzen 原版 vs lalalia 强记忆）在同一预算下表现相近，差异主要在抽样。

## 5. 复现

1. 在 Kaggle 上以 **ARC-AGI-3** 竞赛上下文新建 Notebook，加速器选 **RTX PRO 6000**，**关闭联网**。
2. 上传 `notebooks/arc3-form-d1-t55.ipynb`（或 `arc3-slm-plus-v2.ipynb`）。
3. 挂载竞赛数据与模型 `dfranzen/intel-qwen3.8-flash-next-w4a16-autoround`。
4. 全量运行（约 9 小时），产物 `submission.parquet` 自动生成。
5. 提交后由 Kaggle 在私有测试集上重跑评分。

> 注意：`SERVER_STARTUP_TIMEOUT` 必须 ≥ 3300 秒。设为 720 秒会导致模型未就绪即开始交互，产出全零提交。
